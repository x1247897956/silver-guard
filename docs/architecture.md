# SilverGuard 架构说明

> 本文回答四个问题：**系统由哪些部件组成**、**一次判定要经过哪些步骤**、
> **哪些东西是确定性的哪些不是**、**状态存在哪里**。
> 数字与实验结论见 `docs/eval-report.md`；为什么这么切分见 `docs/design-notes.md`。

---

## 1. 一次判定（POST /assess）的完整路径

```
客户端提交多轮轨迹 turns[]
        │
        ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 0. 预处理（确定性）                                                    │
│    · extract_identifiers()：从轨迹里抽出"真实出现过的"标识符            │
│      → 之后工具只接受这些值（禁止模型自造标识）                          │
│    · MemoryStore.ensure_session()：建立/读取会话状态（当前等级、已触发动作）│
└───────────────────────────────────────────────────────────────────────┘
        │  逐轮推进（模拟旁路监督：每一轮都重新判定一次）
        ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 1. 证据抽取（**不确定**：LLM 调用）                                     │
│    prompts.EVIDENCE_SYSTEM + 增量轨迹 → 结构化 JSON                     │
│    输出：signals[{type, quote, turn_index, confidence}] / suggested_level │
│    纪律：quote 必须是原文逐字片段；不确定的维度宁可不报                  │
└───────────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 2. 确定性证据补齐（**确定**）                                           │
│    · _rule_signals()：把话术规则命中转成信号（与 check_fraud_pattern 同源）│
│    · detect_compromise()：老人"已被说服"的语言特征（本人转述/答应操作）   │
│    为什么要有这一步：策略表的输入必须可复现，不能只依赖模型判断            │
└───────────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 3. 工具调用（**确定**触发，工具本身可能失败）                            │
│    check_fraud_pattern(累积文本) → pattern_hit                          │
│    check_contact(identifier)     → 是否白名单/是否首次出现               │
│    get_elder_profile(elder_id)   → 档案/白名单/历史事件/近期支出（仅 D 组）│
│    notify_family(...)            → 等级 ≥L3 才允许（不可逆动作需授权）    │
│    每一次调用都记：名 + 参数 + 返回 + 耗时 + 重试次数 + 是否降级          │
└───────────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 4. 策略引擎（**确定**，本次判定的唯一决策点）                            │
│    PolicyContext{信号集合, pattern_hit, victim_compromise, suggested_level, │
│                  current_level}                                        │
│        → PolicyEngine.decide()                                         │
│    规则来自 config/policy.yaml（热加载 + 版本号）                        │
│    · mode=policy     ：规则决定等级（LLM 建议只能被拒，不能被采纳升级）    │
│    · mode=llm_only   ：**对照实验**，采纳 LLM 建议（"关掉策略引擎"）       │
│    · 单调不降：等级低于会话当前值 → 维持当前值，并记录"降级诱导被拦"       │
│    · 授权检查：不可逆动作需要 strategy 声明的授权等级                     │
└───────────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────────┐
│ 5. 落库与可观测（**确定**）                                             │
│    action_log：状态迁移（前值→后值、触发理由、策略版本）                  │
│    runs：每案一行，含 prompt / 模型 / 策略三个版本号 + 延迟 + tokens      │
│    data/runs/<config>__<case_id>.json：完整轨迹（含模型输出缓存，供回放）│
└───────────────────────────────────────────────────────────────────────┘
```

**确定性边界（重要）**：整条链路上**只有第 1 步不确定**。第 2、3、4、5 步都是确定性的。
这就是"指标掉了我能说清是哪一版引起的"这句话的技术前提。

## 2. 部件与职责

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| `config.py` | 环境变量、路径、`PROMPT_VERSION` | 版本号必须与 prompt 改动同步提升 |
| `policy.py` | 策略表加载/热加载/校验/决策/授权 | 解析失败保留旧策略；不可逆动作必须声明授权等级 |
| `agent.py` | 四段式链路 + 四组消融配置 | LLM 建议不可越过规则；等级单调不降 |
| `tools.py` | 工具注册表 + schema 校验 + 权限 + 幂等 + 容错 | 参数当不可信输入；不可逆动作需授权等级 |
| `memory.py` | SQLite：档案/白名单/事件/支出/会话状态/runs/action_log | 会话状态是唯一可变状态，全部落库 |
| `context.py` | 上下文预算：分段摘要 + 状态外置 + 工具结果裁剪 | 压缩必须同时给出 tokens 与指标代价 |
| `metrics.py` | 指标确定性计算 + Badcase 分类 | 不经 LLM 判分 |
| `runner.py` | 评测编排：消融、阈值扫描、引擎开关、门禁 | 门禁比对基线，掉线即非零退出 |
| `redteam.py` | 自动红队共演进 + 老人模拟器 | 变异样本单独落盘；heldout 全程封存 |
| `replay.py` | 确定性回放与一致率 | 固定三版本号；不一致案例单独列出 |
| `service.py` | FastAPI + WebSocket | 无 key 时 `/intervene` 降级为模板并如实标注 |
| `mcp_server.py` | 以 MCP 暴露四个工具 | 与内部工具层**同一份实现**，无二套逻辑 |

## 3. 状态在哪里

三类状态，分得刻意很清楚：

| 状态 | 存放 | 生命周期 | 谁写 |
| --- | --- | --- | --- |
| **会话状态**（当前等级 / 已触发动作 / 已确认事实） | `session_state` 表 | 单次会话（case_id + config） | 策略引擎经由 `_apply()` |
| **长期记忆**（档案 / 白名单 / 历史事件 / 支出） | `elders` `contacts` `events` `transactions` | 跨会话 | 记忆层写入，工具层读取 |
| **运行痕迹**（状态迁移 / 工具调用 / 指标） | `action_log` `runs` + `data/runs/*.json` | 永久（评测复用） | 全链路 |

会话状态是**唯一**会被判定过程修改的状态。它只做两件事：

1. **单调不降**：`level = max(level, decision.level)`。要降级必须改策略表（`policy.monotonic: false`），
   这条路径在正常配置下不可达。
2. **干预幂等**：`notify_family` 的幂等键 = `hash(elder_id | action | target)`，
   TTL 内重复触发直接被拦（`idempotent_skip`），避免反复打扰家属。

## 4. 评测链路

```
eval/dataset/{attack,benign}.jsonl   （进 git，带 sha256；dev/heldout 划分冻结）
        │
        ├──► runner --configs A,B,C,D ──► 四组消融对照表
        │        A rule         正则命中 → 策略表（零 LLM）
        │        B single_llm   整段轨迹一次调用，无工具无记忆
        │        C agent        逐轮 LLM + 工具
        │        D agent_memory C + 长期记忆
        │
        ├──► runner --thresholds ──► 3–5 组阈值下的（漏拦率, 误报率）
        ├──► runner --matrix     ──► 策略引擎 开/关 对照（SE-ASR）
        ├──► redteam --rounds 2  ──► 绕过率曲线 + heldout 封存复测
        ├──► replay              ──► 回放一致率
        └──► runner --gate       ──► 与 eval/baseline*.json 比对，掉线即 fail
```

`docs/eval-report.md` 是上述所有数字的**唯一出处**。

## 5. 容量与边界（如实声明）

- 单进程、单机、SQLite 单文件；**没有分布式、没有高并发设计的宣称**。
- 评测规模是"数百条合成样本"，不能据此量化真实人群中的效果。
- 不做向量检索、不做微调、不做端侧推理——这些不是本项目要回答的问题（见 `design-notes.md`）。
- `notify_family` 是 mock：接口真实、通道不存在。
